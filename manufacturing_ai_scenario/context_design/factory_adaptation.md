# 製造業議事録のClaudeFactory適応設計

**作成**: 2026-05-09 / Sonnet 4.6
**信頼度**: [DRV] — ClaudeFactory設計文書と4プロジェクトからの構造導出

---

## 1. 概要

製造業の5部門（営業・開発・設計・製造・研究）の議事録を、ClaudeFactoryのパイプラインで処理する。4プロジェクト（①-A/①-B/②/③）がそれぞれFactory内の異なる機能として動く。

---

## 2. 5部門の議事録が持つ情報の性質

| 部門 | 議事録の中身 | 情報の性質 | リスク級 |
|---|---|---|---|
| 営業 | 顧客要求、クレーム、市場動向、競合情報、納期交渉 | 外部起点・時間制約あり・事実と推測が混在 | 鶏級 |
| 開発 | 製品企画、フィージビリティ、要求仕様、DR結果 | 決定と仮説が混在・「やれそう」が「やれる」に化けるリスク | 鶏〜フグ級 |
| 設計 | 設計仕様、FMEA、公差検討、材料選定、強度計算根拠 | 定量的根拠あり・ただし前提条件の省略リスク | ピザ〜鶏級 |
| 製造 | 工程異常、品質データ、設備稼働、4M変更、是正処置 | 事実ベース・ただし原因推定が混入しやすい | ピザ〜鶏級 |
| 研究 | 実験結果、技術シーズ、特許調査、論文引用、仮説検証 | Think(x)主体・Meas(x)との紐付けが必要 | 鶏〜フグ級 |

## 4. 部門別の具体的な処理

### 4.1 営業の議事録

**典型的な内容**: 「顧客Xが○○と言っている」「競合Yが△△を出した」「納期を1ヶ月前倒しできないか」

**Factory内での処理**:

| 処理 | 内容 |
|---|---|
| Airlock | 「顧客が言った」は[OBS]。「顧客の要求仕様」に昇格させない。営業の解釈は[DRV] |
| Curator | 発言者（営業担当）・情報源（顧客名/展示会/競合カタログ）・主張・根拠を分離 |
| Resolution | 顧客要求と既存仕様の矛盾検出。「納期前倒し」と「品質基準維持」の両立可能性 |
| Critic | 「顧客が求めている」と「営業が売りたい」が混同されていないか |

**お好み焼き偽装リスク**: 営業が最も高い。「顧客の声」が「営業の希望」にすり替わる。Airlock段階で発言者と情報源を厳密に分離する。

### 4.2 開発の議事録

**典型的な内容**: 「新素材Aで軽量化できそう」「コスト試算はまだだが方向性としてはOK」「DR1通過」

**Factory内での処理**:

| 処理 | 内容 |
|---|---|
| Airlock | 「できそう」は[EST]。DR通過は[FACT]。フィージビリティ結果は[OBS]か[DRV] |
| Curator | 決定事項・保留事項・宿題の3分類。DR議事録はDR番号と判定結果を構造化 |
| Resolution | 開発方針と設計制約の整合性検証。「軽量化」と「強度基準」の両立をFOLで検査 |
| Critic | 「方向性OK」が「正式承認」に化けていないか。前提条件（コスト未試算）が落ちていないか |

**フグ級論点**: 開発のフィージビリティは本質的に[EST]。「やれそう」を「やれる」に昇格させるにはMeas(x)（試作・実験・計算）が必要。

### 4.3 設計の議事録

**典型的な内容**: 「FMEAでリスクBと判定」「公差±0.05に変更」「材料をSUS304からSUS316に変更。理由は耐食性」

**Factory内での処理**:

| 処理 | 内容 |
|---|---|
| Airlock | 設計根拠あり→[FACT]〜[OBS]。ただし前提条件（使用環境、荷重条件）の省略がないか確認 |
| Curator | 変更事項・変更理由・影響範囲・関連図番の構造化 |
| Domain | ①-A 畑村の設計方法論で「本来検討すべきだった観点」を補完。設計のナレッジマネジメント |
| Resolution | 設計変更と上流要求（顧客仕様、法規制）の整合性をFOLで検証 |
| Critic | 設計根拠が実験/計算に基づくか、経験則だけか。経験則は[DRV]止まり |

**①-A直結**: 畑村の「実際の設計」が最も効く部門。設計判断の背景知識をRAGで供給する。

### 4.4 製造の議事録

**典型的な内容**: 「ロットNo.XXXで寸法NG 3/100個」「4M変更: 作業者交代」「是正処置: 治具改修」

**Factory内での処理**:

| 処理 | 内容 |
|---|---|
| Airlock | 品質データは[FACT]。原因推定は[DRV]〜[EST]。「たぶん治具が原因」を[FACT]にしない |
| Curator | 不具合事象・発生条件・暫定対策・恒久対策・水平展開の構造化 |
| Resolution | 是正処置と根本原因の論理的整合性検証。「治具改修」で本当に再発防止になるか |
| Critic | 原因推定の信頼度検査。n数1の不具合で恒久対策を決めていないか |

**最もピザ級に近い**: 製造データは測定値ベース。ただし原因分析（なぜなぜ）が入ると[DRV]になる。

### 4.5 研究の議事録

**典型的な内容**: 「実験結果: 引張強度15%向上（n=5）」「論文Zの手法を適用検討中」「特許調査: 先行例3件」

**Factory内での処理**:

| 処理 | 内容 |
|---|---|
| Airlock | 実験データは[OBS]（n数と条件を記録）。「適用検討中」は[EST]。特許情報は[LIT] |
| Curator | 実験条件・結果・考察の3分離。考察は[DRV]。Source Cardに論文出典を紐付け |
| Domain | ①-B 形式論理学で仮説の論理構造を検査（前提→結論の妥当性） |
| Resolution | 研究仮説と既知の工学原理の整合性をFOLで検証 |
| Critic | n=5で「向上した」と結論づけてよいか。統計的検定の有無。再現性の確認 |

**Think(x)とMeas(x)の境界**: 研究は仮説（Think）と実験（Meas）の往復。議事録では両者が混在する。

## 6. 部門間矛盾の導出例

### 例1: 営業×設計の矛盾

```
営業議事録: 「顧客Bは納入品の肉厚3mm以上を要求」
設計議事録: 「軽量化のため肉厚を2mmに変更（DR2承認済み）」

Airlock:
  営業側 → ∀x(ForCustomerB(x) → MinThickness(x, 3mm))  [OBS]
  設計側 → ∀x(ProductA(x) → Thickness(x, 2mm))         [FACT: DR承認]

Resolution Worker:
  顧客Bの製品AについてCNFに変換:
    {ForCustomerB(a), ProductA(a)}  （事実）
    {¬ForCustomerB(x) ∨ MinThickness(x, 3mm)}  （営業）
    {¬ProductA(x) ∨ Thickness(x, 2mm)}  （設計）
    {Thickness(a, 2mm) ∧ MinThickness(a, 3mm)}  → 矛盾（2mm < 3mm）

  → □（空節）を導出
  → 報告: 「設計変更(2mm)と顧客要求(3mm以上)が矛盾」

Critic:
  設計のDR2承認は顧客Bの要求を考慮していたか？
  営業の「顧客要求」は仕様書に記載されているか口頭か？
  → 差し戻し: 設計に顧客要求の確認を依頼
```

### 例2: 開発×製造の矛盾

```
開発議事録: 「新素材Aの採用を決定（強度15%向上）」
製造議事録: 「新素材Aの加工条件が未確立。現行設備では切削不可の可能性」

Airlock:
  開発側 → Adopted(MaterialA) ∧ StrengthImprovement(MaterialA, 15%)  [FACT: 決定]
  製造側 → ¬Established(MachiningCondition(MaterialA))  [OBS]
           ◇¬Machinable(MaterialA, CurrentEquipment)     [EST]

Resolution Worker:
  Adopted(MaterialA) ∧ ¬Established(MachiningCondition(MaterialA))
  → 矛盾ではないが、前提条件の欠落を検出
  → 報告: 「素材Aの採用決定に製造可否の検証が含まれていない」

Critic:
  開発の「決定」は製造フィージビリティを条件としているか？
  → 差し戻し: 開発に製造条件確認のアクションアイテムを付与
```

## 7. Worker prompt設計への入力（§10.2向け）

この適応設計から、以下のWorker promptの仕様が導出される。

| Worker | 製造業向けの追加判断基準 |
|---|---|
| Airlock Agent | 部門タグ（営/開/設/製/研）付与。部門固有のお好み焼き偽装パターン検出 |
| Curator Agent | DR番号、図番、ロットNo.の構造化抽出。アクションアイテムの担当部門紐付け |
| Domain Agent | 製品別×工程別×顧客別の3軸分類。部門横断リンク（クレーム↔不具合↔設変） |
| Resolution Worker | 部門間矛盾検出に特化。仕様矛盾、日程矛盾、コスト矛盾の3パターン |
| Critic Agent | 信頼度タグと部門の対応検査。営業の[OBS]が設計の[FACT]に化けていないか |

## 8. 導入順序

Phase 0で最も効果が高いのは**営業×設計の矛盾検出**。理由:

1. 製造業で最もコストがかかる不具合は「顧客要求と設計仕様の不一致」
2. この不一致は後工程（製造・出荷後）で発覚するほど損害が大きい
3. 議事録レベルで矛盾を検出できれば、DR段階で是正できる
4. FOL変換の対象が比較的単純（数値仕様の大小比較）でフグ級リスクが低い

```
Phase 0: 営業議事録×設計議事録の矛盾検出（②-αプロトタイプ）
Phase 1: 開発×製造の矛盾検出を追加
Phase 2: 研究→開発の技術移転判定を追加
Phase 3: 全5部門の横断分析
```
